## Phase 1 answers

**Which tables hold the foreign keys?**

Stages hold festival_id. Tracks hold artist_id. Tickets hold attendee_id and festival_id. Performances hold stage_id and artist_id.

**Why do foreign keys belong on the many side?**

Each child points to one parent. Several children can store the same parent's ID, so the parent does not need to store a list of child IDs.

**Which tables must be migrated first, and why?**

Festivals must exist before stages and tickets. Artists must exist before tracks and performances. Attendees must exist before tickets. Stages must exist before performances. We used the required order: festivals, stages, artists, tracks, attendees, tickets, performances.

## Nested route answers

**Pair A:** GET /festivals/:festival_id/stages lists a festival's stages. The parent's ID is params[:festival_id].

**Pair B:** GET /artists/:artist_id/tracks lists an artist's tracks. The parent's ID is params[:artist_id]. An individual track uses /tracks/:id, where params[:id] is the track's ID.

**Pair C:** GET /attendees/:attendee_id/tickets lists an attendee's purchase history, with the parent's ID in params[:attendee_id]. GET /festivals/:festival_id/tickets lists a festival's ticket sales, with the parent's ID in params[:festival_id].

**Performance:** GET /stages/:stage_id/performances and GET /artists/:artist_id/performances list performances for a stage or artist. The parent parameters are params[:stage_id] and params[:artist_id].

## Reflections

**a. In each relationship, which table holds the foreign key, and why that table?**

Stages have festival_id because each stage belongs to one festival. Tracks have artist_id because each track belongs to one artist, while an artist can have many tracks. Tickets have attendee_id and festival_id because each ticket belongs to one attendee and one festival. Performances have stage_id and artist_id because each performance connects one stage and one artist. The foreign keys go on the many side so each child can point to its parent.

We used dependent: :destroy so deleting an artist also deletes its tracks.

**b. What happens to a Festival's Stages when the Festival is destroyed? Where in your code did you specify that behavior?**

Destroying a festival also destroys its stages because the Festival model uses has_many :stages, dependent: :destroy. If the festival has tickets, has_many :tickets, dependent: :restrict_with_error blocks deleting the festival, so its stages stay too.

**c. Why does `Performance` need to be its own model with its own table, rather than a bare join table with no model?**

Performance stores starts_at along with stage_id and artist_id, so it represents a scheduled performance. Its own model lets us validate the start time and connect stages and artists using has_many :through.

**Pair B only: what changed in `rails routes` when you used `shallow: true`?**

Listing and creating tracks still use the artist's ID in the URL. Viewing, updating, and deleting a track only need the track's ID, so those routes are no longer nested under an artist.

**Pair C only: why might tickets be nested under both Attendee and Festival?**

Each ticket belongs to both an attendee and a festival. The attendee route shows one attendee's purchase history. The festival route shows one festival's ticket sales.

## Model source listing

### app/models/festival.rb

```ruby
class Festival < ApplicationRecord
  has_many :tickets, dependent: :restrict_with_error
  has_many :stages, dependent: :destroy

  validates :name, presence: true
  validates :city, presence: true
  validates :starts_on, presence: true
end
```

### app/models/stage.rb

```ruby
class Stage < ApplicationRecord
  belongs_to :festival
  has_many :performances, dependent: :destroy
  has_many :artists, through: :performances

  validates :name, presence: true
  validates :capacity, numericality: { only_integer: true, greater_than: 0 }
end
```

### app/models/artist.rb

```ruby
class Artist < ApplicationRecord
  has_many :tracks, dependent: :destroy
  has_many :performances, dependent: :destroy
  has_many :stages, through: :performances

  validates :name, :genre, presence: true
end
```

### app/models/track.rb

```ruby
class Track < ApplicationRecord
  belongs_to :artist

  validates :title, presence: true
  validates :length_sec, numericality: { only_integer: true, greater_than: 0 }
end
```

### app/models/attendee.rb

```ruby
class Attendee < ApplicationRecord
  # Tickets are purchase records, so block deleting an attendee who has any
  has_many :tickets, dependent: :restrict_with_error

  validates :name, :email, presence: true
end
```

### app/models/ticket.rb

```ruby
class Ticket < ApplicationRecord
  belongs_to :attendee
  belongs_to :festival

  validates :tier, presence: true
  validates :price_cents, numericality: { only_integer: true, greater_than_or_equal_to: 0 }
end
```

### app/models/performance.rb

```ruby
class Performance < ApplicationRecord
  belongs_to :stage
  belongs_to :artist

  validates :starts_at, presence: true
end
```
